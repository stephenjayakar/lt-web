# EOtF engine fork vs upstream lt-maker: structured diff

EOtF v2.0.0 (`lt-maker/eotf.ltproj`, EOtF repo d9d2975) runs on a private fork of
Lex Talionis. The closest source we have is the fork's v1.90 Windows build
(`~/Desktop/EotF/app`, 581 .py files, `VERSION = "1.9.5"`). The web was ported from
upstream `lt-maker/` (b811e266, 2026.02.17a). Policy (PARITY-REPORT.md): where the
engines disagree, the web follows the fork.

## Method

1. **Fork base.** Hashing every fork `.py` (CRLF normalised) against every upstream
   commit's tree found the closest base: `5078af9f` (2024-02-04), 377/581 files
   byte-identical (2024.06.02a matches 330). A few stale files in the build
   (`events/event_parser.py`, `python_eventing/compilation.py`) predate it and are
   not imported.
2. **Three-way diffs.** For every differing file under `app/{engine,events,data,utilities}`
   (editor code excluded): base→fork (fork changes), base→upstream HEAD (upstream
   changes after the fork) and upstream→fork. 284 files differ: 78 carry fork
   changes, 269 carry upstream changes after the fork (66 both, 12 fork-only,
   203 upstream-only). Most upstream churn is refactoring (type hints, renamed
   helpers, `arrive`/QuickArrive, pair-up, editor hooks) with no EOtF effect.
3. **Classification** of each behavioural difference: *fork-only feature*,
   *upstream change after the fork* (the fork keeps the 2024 behaviour), or
   *fork customization* (the fork changed base behaviour). A fourth class turned
   up often: *web bug* — both Python engines agree and the web follows neither.
4. **EOtF exercise.** Each row was checked against EOtF data: `game_data/*.json`
   (components, events, constants, equations, ai), and the project-local
   `resources/custom_components/*.py`.
5. **Assets.** Engine sprites compared by SPRITES name (pixel-decoded), fonts
   (glyph sheets, `.idx`, palettes) and platforms; see "Engine assets" below.

Gating: fixes for fork-specific behaviour check `isForkEngine()`
(`src/engine/engine-flavor.ts`, true when the project's metadata names EotF), so
default.ltproj and rekka keep upstream behaviour. Web bugs are fixed for every
project.

  upstream 122x48) and `menu_bg_parchment` (48x30 vs 48x32) differ;
  `menu_bg_base` differs only in encoding. Fork-only: `LevelScreen2`,

  `unit_select_base/glow`, `unit_selector_glow`, `info_equipment_highlight`,
  `old_unit_info_bg`, `damage_numbers_extra_purple`, `combat_stats_<color>_guard` (×4,
  unused: pairup off). 112 upstream-only sprites (colored turn banners, new
  colored forecast windows, prep window art...) are newer upstream features; the
  web uses them only through fallbacks that resolve to the shared names for EOtF.
- **Fonts**: the fork keeps them engine-level (`resources/fonts/*-<color>.png` + `.idx`
  + palettes in `fonts.py`); every glyph sheet and `.idx` matches upstream's
  `default.ltproj/resources/fonts` and the palettes map the same colour pairs (listed
  in a different order). No overlay needed.
- **Platforms**: identical. **Autotiles**: editor-only.
- **public/sprites** (web copies): all match both engines.

## Appendix: Combat core and formulas

Scope: `engine/combat/*`, `engine/combat_calcs.py`, `engine/equations.py`, `engine/component_system/*`, the fork's generated `engine/item_system.py` / `engine/skill_system.py`, and the parts of `engine/item_funcs.py` and heal components that change combat numbers. I compared the fork (`/Users/stephen/Desktop/EotF/app`) with the base commit 5078af9f and upstream HEAD using the `temp/forkdiff/*.diff` files plus a direct read of both trees. EOtF usage counts come from `lt-maker/eotf.ltproj/game_data/*.json` and `resources/custom_components/*.py`. The relevant EOtF constants are `def_double=True`, `min_damage=1`, `glancing_hit=False`, `pairup=False`, `lead=False`, `support=False` and `line_of_sight=False`. The only difficulty mode uses `rng_choice="True Hit"`.

Hook tables: a scripted check found that the fork's generated `item_system.py` and `skill_system.py` match the fork's `compile_*_system.py` exactly, with no policy or default mismatches. Every hook-level difference from upstream is in the table below. Hooks with the same policy in fork and upstream (all `modify_*` and `dynamic_*` hooks are NUMERIC_ACCUM, the multipliers are NUMERIC_MULTIPLY, the formula hooks are UNIQUE, `canto_movement` is MAXIMUM) also resolve the same way in `src/combat/*-system.ts`: UNIQUE takes the last active value, and the others sum, multiply or take the max as expected.

Web line numbers are from 2026-10-26. `combat-solver.ts`, `game-states.ts` and `map-combat.ts` were being edited by someone else while I worked, so their line numbers may shift. Grep treats `src/events/event-manager.ts` as a binary file, so search it with `grep -a`.
