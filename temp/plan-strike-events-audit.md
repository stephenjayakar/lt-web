# EOtF combat strike-event audit (2026-10-26)

Every distinct event script EOtF triggers through `event_on_hit` (218 item
uses), `event_on_strike` (1 skill use) and `event_before_combat` (7 item and
23 skill uses), classified by whether its timing can change a later strike,
the end-of-combat results, or what the player sees mid-combat.

Timing contract (lt-maker and EOtF's own engine, v1.90 `app/engine/combat/`,
agree):

- `event_on_hit` / `event_on_strike` fire inside `CombatPhaseSolver.do()`.
  The EventStates run after the phase's rolls and damage are computed but
  before its actions (HP loss, etc.) apply and before its hit is shown; the
  next phase is solved afterwards, against whatever the events changed. A
  phase's triggers run newest first.
- `event_before_combat` (EOtF custom item/skill component) fires in
  `start_combat`, so it runs before the first phase is solved, after
  `combat_start` (pushed later, so run first).

Web before 2026-10-26: every strike was solved in the combat's constructor;
strike events ran after the last strike and after the end-combat hooks; before
combat events were queued before the solve but only ran once the strike events
ran at clean_up0. The verdict column below describes the difference against
that old web behaviour; `qa/strike-events` makes the web follow the contract
above for map and animation combat.

Verdict key: NONE = timing cannot change anything observable; VISUAL = only
presentation order (dialogue, menus, animations shown before the hit in
Python, after the combat on the old web); STATE = state or outcome differed.
"BC" marks event_before_combat rows.

Verdicts: NONE 51, VISUAL 121, STATE 29 (201 scripts; Ability_Serve_Forth moved from STATE to VISUAL on review). All STATE and VISUAL rows now follow Python's timing on the web; see the bottom of this file for what remains.

## Remaining differences after `qa/strike-events`

- `interact_unit ...;immediate` combats still solve every strike at once and
  run their strike events afterwards.
- (Fixed in `fix/dev-combat`: each phase is solved with the units showing
  the simulated HP earlier phases left, including the striker's lifelink.)
- Start-combat hooks are triggered skills-first then items-first for all
  participants; Python interleaves skill and item hooks per participant, so
  two before-combat events on different participants can run in a different
  order.
- Nested combats share one CombatState instance (saved/restored): while one
  runs, the waiting combat below it is not drawn.
- The map combat's lookahead for the camera (`panBack` in animation combat)
  cannot see past a phase whose events have not run yet.
- End-of-combat ordering follows lt-maker's split clean_up0/1/2 (commit
  3ba6d92). EOtF's engine has one `clean_up()` and no `combat_death`
  trigger (v1.90 `app/engine/combat/simple_combat.py`); its CombatEnd,
  end_combat hooks, exp and dying states are pushed in a different order.
  Not changed here.
